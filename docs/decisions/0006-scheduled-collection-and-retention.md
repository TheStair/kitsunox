# 0006: Hourly chained collection, with 7-day blob retention

**Date:** 2026-10-27
**Status:** Accepted (user chose "hourly, with retention")
**Resolves:** roadmap open decision 5 (blob retention); starts roadmap Phase 9

## Context

The first real 24h run produced no malicious samples. npm removes malicious releases within
hours, and the run fetched each packument once, at the end of the day. To catch releases before
the takedown, ingest has to run often. Storage measured on that run: 5.5 GB of zstd packument
blobs and 0.8 GB of `changes.jsonl` per day, with 281 GB free on the machine.

## Decision

- **`kitsunox collect`, hourly, via a launchd agent** (`local.kitsunox.collect`, generated by
  `kitsunox schedule plist`). Each tick:
  - rebuilds the watchlist if it is more than 7 days old;
  - syncs labels if they are more than 20 hours old;
  - records one chained ingest run;
  - prunes if the last prune was more than 20 hours ago.
- **Chained runs.** The checkpoint stores the previous run's id and `as_of`. A chained run
  reads the feed from that checkpoint, and its window starts 15 minutes before the previous
  run's `as_of`. The overlap catches releases that reached the feed a little after their publish
  time; duplicates are deduplicated when datasets are built. Because the feed ranges are
  contiguous, `window_covered` is true by construction. After a gap of more than 48 hours (e.g. the
  machine was off), the run falls back to a normal 24h window. Releases from earlier in the gap
  are not recorded, and the log line says "NOT chained", so the gap is visible.
- **Retention: 7 days of full replayability**, then for each older run:
  - **pin** the packument blobs of packages named in any OSV record;
  - **compress** `changes.jsonl`;
  - **delete** every blob no remaining run references.
  Pruned runs refuse to replay with a clear error.
- **A lock on the data directory** (`flock`). Pruning deletes blobs that no snapshot references,
  and a run still recording has exactly such blobs. `ingest record`, `data prune` and `collect`
  take the lock; a `collect` tick that finds it held exits quietly.

## Why 7 days, not the 30 proposed earlier

The 30 days in the roadmap matched the benign-label delay, assuming evaluation would need raw
packuments. It doesn't: datasets use the `Change` records, which keep every in-window version's
manifest and are kept forever (compressed). Raw bodies are only needed for:

- **replay**, which validates determinism and is exercised within days;
- **analysing malicious samples later**, which pinning covers, provided the OSV record exists by
  the time the run is pruned. Most records appear within 1–2 days.

7 days costs about 40–45 GB at steady state; 30 days would cost about 165 GB. The setting is
`--keep-days` on `collect` and `data prune`.

## Consequences

- **Tarballs are not captured.** A malicious sample caught by collection has its metadata and
  packument, but not its code, which is gone once npm removes it. Code-level stages (2–3) will
  need tarballs downloaded at ingest time, at least for changes forwarded past Stage 1. That is
  part of the forward policy, to be built with Stage 1/2.
- **Runs older than 7 days can't be replayed**, except for their pinned packuments.
- The laptop must be awake. A gap under 48 hours loses nothing, because the next tick's window
  stretches back to the previous run. A longer gap loses everything before the last 24 hours,
  and the log shows "NOT chained".

## Addendum (2026-10-27): tarballs

Superseded in part by [0008](0008-stage2-routing-and-tarball-capture.md): `collect` now runs
Stages 1 and 2 each tick and captures tarballs. They are recorded per run in
`static-snapshot.json` and follow the same rules: 7 days, then pinned only for OSV-named
packages. The immutable index no longer counts as a reference during garbage collection.
Before this change, it would have kept every tarball forever.

## Addendum (2026-10-28): gaps and network failures

[0009](0009-network-failure-handling.md) raises the chain gap from 48 hours to 7 days, retries
packages and tarballs that failed because of the network, and makes offline ticks write nothing.

## Addendum (2026-10-29): repository archives

Stage 4's GitHub archives turned out to be ~31 GB a day (one live day, 2,142 archives,
dominated by monorepos that release many times a day), which at 7 days is more than this
machine's free disk. They get their own setting, `--keep-repo-days` on `collect`,
`data prune` and `schedule plist`: the default stays `--keep-days` (7), and the local laptop
agent uses 2 until collection moves to a VM with room. A run older than that keeps everything
else, but its Stage 4 can no longer be replayed from cache: the archives would be fetched again
(they are immutable by commit, so the result is the same unless the repository is gone).

## Addendum (2026-10-29): collection moves to a Linux VM

Collection now runs on an Ubuntu VM on the user's desktop (4 vCPUs, 30 GB RAM, 357 GB free),
the host planned for the Stage 5 sandbox. The scheduler is a systemd user timer
(`kitsunox schedule systemd`, same command line as the launchd agent; see
[stages/ingest.md](../stages/ingest.md)). Retention: runs and tarballs 7 days, repository
archives **4 days** (`--keep-repo-days 4`). Estimated at ~14 GB/day of tarballs and ~31 GB/day
of archives, that is about 100 + 125 GB, leaving room for heavy days. The VM started a **new
chain**; the laptop's `data/` was not copied (see the devlog).

## Addendum (2026-11-04): the disk filled; 2-day retention and a disk guard

The estimate above was wrong by about half. On 2026-11-03 data reached 373 GB of a 393 GB
disk with nothing yet old enough to prune, and a full disk crashed the VM twice (05:03 UTC
during an hourly tick, and again after a 10-hour catch-up tick of 55k changes). The first
crash left renamed files empty (`atomic_write` doesn't fsync), among them a Stage 4 snapshot,
and garbage collection deliberately stops when a snapshot can't be read, so every later prune
failed and nothing could be freed.

- **Retention is 2 days** for runs and repository archives (the owner's choice), on the timer
  through the new `--keep-days` of `schedule systemd`/`schedule plist`. A 2-day prune freed
  188 GB (373 → 194 GB used). The review queue keeps its own 7-day window (`QUEUE_DAYS`):
  a pruned run keeps its report, but tarballs of versions older than 2 days are gone unless
  their package has an OSV record.
- **Disk guard in `collect`** (`util/disk.py`): free space is measured at the start of each
  tick, before each stage step and before Stage 5. Below 60 GB the tick prunes first (and at
  the end); below 25 GB it starts nothing more, and the skipped runs resume on a later tick.
  The blob store, which takes almost all of a tick's bytes, refuses writes below 10 GB
  (`DiskSpaceError`, which per-package handlers pass on), so a single large stage can't fill
  the disk either.
- **Monitoring:** every tick logs free space; the tick log, the daily summary (a *Disk free*
  field and a *Needs attention* entry) and an immediate Discord alert (at most every 6 hours,
  decision 0011) carry it.
