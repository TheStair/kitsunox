## 3. The fixes

### N2. `npm.dependency.non-registry` v6: own-scope registry tarballs (Stage 1)

`@atharva-again/pi-coding-agent@1.3.0` and `@atharva-again/pi-tg@0.1.14` depend on
`@earendil-works/pi-ai` from `https://registry.npmjs.org/@atharva-again/pi-ai/-/pi-ai-1.3.0.tgz`:
the author's fork, published to the registry in the author's own scope, pinned by URL. That is
exactly what `"@earendil-works/pi-ai": "npm:@atharva-again/pi-ai@1.3.0"` installs, and an
`npm:` alias is a registry spec (no finding). The URL is fetched from the registry, where
takedowns apply; only the scope's owner can publish into `@atharva-again`; and the target is a
release in the feed that Stages 1-3 read like any other. v6 makes it LOW, weight 1, with a note.

Kept MEDIUM: a tarball of a package in another scope or an unscoped one (Stage 4's
`known-malware`, `fresh-foreign` and `missing` follow `npm:` aliases but not URLs, so they
would not see it), a look-alike host (`registry.npmjs.org.evil.test`), an unscoped dependent.
Same-name registry tarballs were already no finding (v2).

Live: `@atharva-again/pi-coding-agent@1.3.0` (score 4 → 2) and `@atharva-again/pi-tg@0.1.14` (4 → 1; both its URL dependencies are own-scope tarballs) are no longer reported. `vm-day1`: no sample has a registry tarball dependency (all 3,444 scanned).

### G1. `npm.provenance.githead-dropped` v2: weight 1 beside a downgrade (Stage 4)

The score-only bucket (40 benign, 2 positives) is a `WEAK_ALONE` MEDIUM plus LOWs at the cap.
37 of the 40 benign are a MEDIUM `npm.publish-method.downgrade` (an unwatched package
hand-published after CI, with a co-signal); 16 of them also carry `githead-dropped` at weight
2, which with the downgrade's 3 and `npm.dependency.added`'s 1 makes exactly 6.

| live positives | 1 of 4 (`@hithink-tech/hithink-finance-cli@0.2.0`) | |
| `vm-day1` malicious samples | 34 of 149 | 23% |

(For contrast, `npm.dependency.added` given a downgrade: 46 of 273 benign, 17%, against 107 of
149 malicious, 72%: it does separate, and is untouched.) Both rules then report one event, the
release leaving the CI path, and the downgrade already uses the dropped `gitHead` (its

Live: 9 benign versions are no longer reported, each from exactly 6 to 5: a MEDIUM downgrade (3), `npm.dependency.added` or `npm.maintainer.added` (1) and `githead-dropped` (2 → 1). The score-only bucket goes from 40 benign to 31. Positives: `@hithink-tech/hithink-finance-cli@0.2.0` (unwanted) keeps its

## 7. After the freeze: what would cut the commit bumps

The 33 same-account GitHub commit bumps are the largest benign shape left in the cluster
(section 6). A commit pin is immutable, so the fork-plant objection can be answered with one
fact: **the pinned commit is on the dependency repository's default branch** (GitHub's compare
API, which `githost.GitHub.on_branch` already wraps for `repo.established-match`). A commit on
the default branch was pushed by someone with write access, which makes it exactly as trusted
as round 4's tag bumps. This needs a Stage 4 lookup (a new, capped, cached request per pinned
dependency), which the replay harness can't measure offline, so it is not built.
It would **not** save `lane-m-snackager-probe@1.0.1`: the attacker owns that repository, so its
commit is very likely on its default branch. Round 4's N1 has the same exposure for tags
(round 4 C, owner question 2). A rescue would need "the previous release that vouches is
itself established", e.g. the package's first release older than 7 days, which Stage 0 does
not put in the `Change` (a contract change).
