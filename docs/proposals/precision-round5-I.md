## 2. I1: the gyp parser

**The gap** (round 4 B, owner question 4). `install.gyp_commands` took an expansion
`<!(...)` only when its `)` was followed by a quote, lazily, and an action only up to the
first `]`. So `"<!(node payload.js):target"` was never extracted: neither the build-tool
test nor the install-code rules saw that command, and a gyp command expansion is a payload
channel (`@atedone/workspace-bootstrap@0.0.1`, unwanted, ran its payload from a gyp action).
The same laziness made tree-sitter's
`"<!(node -p \"require('node-addon-api').targets\"):node_addon_api_except"` match across
lines into a garbage command, and left escaped quotes (`\'`) in inline code, which the
capability analysis then read as `dynamic-require`.

**The fix** (`ecosystems/npm/gyp.py`; `install.gyp_commands` re-exports it). gyp reads a
`.gyp` file as a Python literal; the parser tokenizes and parses it by hand, never evaluates
it (no `eval`, `ast`, `compile`):

- strings with every Python escape decoded (`\x3c!(` is `<!(`, `<`, octal, `\N{...}`),
  adjacent strings joined (`'<!(no' 'de x.js)'`), raw and triple-quoted strings, `#`
  comments dropped;
- a command expansion in any string (key or value), at any position, inside another
  expansion, in each of gyp's phases (`<!`, `>!`, `^!`, with or without `@`); its end is where
  gyp's `FindEnclosingBracketGroup` puts it (every bracket kind counts, quotes don't); an
  unclosed one runs to the end of the string; the list form `<!(['node', 'x.js'])`, and
  `<!pymod_do_main(module args)` (gyp imports a Python module the package ships);
- each `action` list read whole (an element may hold `]`);
- variables: `<(cmd)` / `<@(cmd)` in a command replaced by the definitions of any
  `variables` dict read (so `'action': ['<@(cmd)']` names what it runs), node-gyp's
  `<(module_root_dir)` by the package root (so `node <(module_root_dir)/scripts/x.js` names
  `scripts/x.js`, which becomes install code);
- the `.gyp`/`.gypi` files a gyp file names (`includes`, `deps/x.gyp:target`), inside the
  package, at most 20;
- a file that does not parse is scanned raw (expansions with the same bracket matching, the
  old action pattern); a file over 256 KiB, or commands over 1,000 / 1 MiB, give a placeholder
  command (`gyp.UNREAD`) that no lookup test accepts (before, an oversized `binding.gyp` gave
  no command at all); every bound is linear (one-pass bracket matching, adjacent strings
  joined once, variable replacement capped at 64 KiB per command), with hostile-input and
  Hypothesis tests (`tests/ecosystems/npm/test_gyp.py`).

**Live effect** (`gyp-main.jsonl` vs `gyp-new.jsonl`: 100 verdicted versions have a gyp file
in a readable tarball, 93 a `binding.gyp`): 59 get different commands, 48 different install
files, 1 a different build-tool result. Most are tree-sitter grammars whose `.targets` lookup the old parser
missed or garbled (now extracted whole, and still a lookup), `nan`/`node-addon-api` lookups
whose `\'` is now decoded, and `node-sword-interface`'s `<(module_root_dir)/scripts/...` (now
read as install code). Decisions (`sub-fix1` vs baseline): **one benign version newly
reported**, `@ohos-ports/distringuish@7.0.0-beta.1`, whose `binding.gyp` has
`"<!(echo $HOME)/.harmonybrew/include/node"`: a shell command reading the home directory, which
the old parser never saw (it was explained by `npm.install-build-tool` only because of that).
That is the parser doing its job; no positive or unverified version changes.
`@ohos-ports/blake-hash@2.0.0-beta.1` loses its `npm.install-script-code` (the inline
`require(\'node-addon-api\')` was `dynamic-require`; decoded it is a header lookup), and is
unreported with I2's `node-gyp-build || exit 0`.

On `vm-day1` (section 5) the old parser already saw every gyp command a malicious sample
runs: 44 samples of one family (`autotel*`, `awaitly*`, `executable-stories-*`,
`@vapi-ai/server-sdk`, ...) have no install hook and run their payload from
`<!(node index.js > /dev/null 2>&1 && echo stub.c)` in `binding.gyp`, which both parsers
extract. I1 closes the suffix form before it is used; it gains nothing measurable today.

## 3. I2: `npm.install-build-tool` v4

What the install-hook-alone and install-hook + install-script-code buckets hold that is a
build or tool hook (`benign-by-rules.tsv`, `bucket.py`): almost all of it is node-gyp
(`node-gyp-build`, `node-gyp rebuild`, with a `binding.gyp` that runs more than a lookup),
two `cmake-js compile`, and singletons. The dev tools the prompt listed (`husky install`,
`patch-package`, `prisma generate`, `ngcc`, `napi build`, `electron-builder install-app-deps`,
`lefthook install`, `is-ci || husky`, `npm run build` of a bundler) are **not among the
reported versions any more** (searched across all 1,428 reported versions' hooks): v1-v3 and
S5 already take them, or they never reached a report. What is left of that list is one
`simple-git-hooks` (`@saltand/lanhu-context-mcp@1.1.0`) and three `patch-package` variants
(`patch-package --error-on-fail`, `yarn patch-package`,
`if command -v patch-package >/dev/null; then patch-package; fi`), both rejected (section 6). The
`npm run x` hooks still reported run package code (`npm run db:generate-migrations` →
`tsx scripts/...`, `npm run install:prebuilt` → `node src/install-prebuilt.js`,
`npm run prepare:native`, `npm run patch && node-gyp ...`), never a known tool, so a "run
script that is a known tool" form would remove nothing (section 6).

v4 (`ecosystems/npm/rules/install_code.py`):

- **`gyp_scripts`**: a `binding.gyp` command other than a header lookup may be
  `node <package script> <constant args>` (`GYP_NODE_FILE`, a full match; no `-e`, no shell,
  no substitution, no redirect) when every such script, and what it loads, only reads the
  package: JavaScript, `plain_text`, not `unreadable`; no capability beyond `filesystem` and
  `os-info` (S5's `INERT`) once the header-lookup inline code is set aside; no package loaded
  by name; nothing that writes, moves, opens or deletes a file (`WRITES`, by name and quoted
  name, so `fs["writeFileSync"]` counts; S5's `DELETES`); none of S5's text guards
  (`RISKY_TEXT`, `SYSTEM_PATH`, `OTHER_PACKAGE`, home references, agent directories); for an
  update, no capability the install code didn't have before. This is how native add-ons list
  the sources of vendored libraries (`<!@(node scripts/sources.mjs zint)`).
- **`PATH_LOOKUP`**: two exact directory prints count as lookups,
  `node -e "console.log(require.resolve('node-addon-api').replace(/[\\/]index.js$/, ''))"` and
  `node -p "require('path').resolve('<relative dir>')"` (no `..`).
- **hook lines**: `node-gyp-build || exit 0`, `JOBS=${JOBS:-max} node-gyp-build`.

Removed (`sub-fix3` vs `sub-fix1`, 8, all benign):

| Change | Versions |
|---|---|
| `gyp_scripts` | `@lakutata/barcode@3.1.6`, `@lakutata/thermal@3.2.1` (`scripts/sources.mjs`: `readdirSync` of vendored source dirs), `btoon@0.1.0` (`scripts/core-path.js`), `@csllc/cs-mccul@0.0.1` (`tools/uldaq-sources.js`) |
| `gyp_scripts` + `JOBS=${JOBS:-max} node-gyp-build` | `@csllc/cs-mccul@1.0.0` |
| `node-gyp-build \|\| exit 0` (+ I1's decoding) | `@ohos-ports/blake-hash@2.0.0-beta.1` |
| `PATH_LOOKUP` | `@ohos-ports/zlib@1.0.5-beta.0`, `pwaos-addon@0.2.0` |

**The positive at risk.** `@atedone/workspace-bootstrap@0.0.1` (unwanted, "covert but
harmless: a gyp action writes local state, written to evade scanners") has
`install: node-gyp rebuild` and a gyp action `node scripts/write-state.js --install`: the

## 6. Rejected

- **`cmake-js compile` as a build tool** (2 benign: `clap-cpp@0.1.1`, `hzt-qywx@1.0.0`).
  cmake-js runs the package's `CMakeLists.txt`, a language with `execute_process`,
  `add_custom_command` and `file(DOWNLOAD)`: `clap-cpp`'s tree (vendored ggml) has 49 such
  calls. Accepting it would need a CMake reader of the same care as the gyp one; not before
  the freeze.
- **`npm run <script>` when the script is a known tool** (prompt's candidate): 0 benign in the
  two buckets or anywhere among the reported versions have a run script that is a known tool
  (section 3); the `npm run` hooks still reported run package code, and `vm-day1` payloads
  run through `npm run` (`eslint-config-sdk@99.0.0`, round 4). Not built.
- **`pkg-config --cflags/--libs` in `binding.gyp`** (`@epotocko/node-libxslt@1.0.0`, 1
  benign): a system tool, neither a dependency nor shipped with npm (the prompt's bar).
- **`<!(echo $HOME)` as a lookup** (`@ohos-ports/distringuish`, the one benign I1 adds): it is
  a shell command reading the home directory; the owner rules home-directory reach relevant.
- **Inert inline gyp code** (`node -p "process.env.X ? 'on' : 'off'"`, `node -e
  "process.stdout.write(process.platform)"`: `@photostructure/heap-trim`,
  `@ohos-ports/apm-bindings`, ~2 benign): the owner dropped inline-code explanations on
  updates (E3, `shoal-cli`); not worth a new exception for two versions.
- **`node-gyp-build || node-gyp rebuild -j max`** (`node-gd@4.0.0`): built, then dropped: its
  `binding.gyp` runs `./util.sh`, so the line removes nothing.
- **`git config core.hooksPath ...`, `bunx bun-git-hooks`, `simple-git-hooks`** (4 benign):
  they point the consumer's repository at hooks or install them there (round 4 B, rejected
  for the same reason); `patch-package` variants (`teleton@0.11.8`'s
  `patch-package --error-on-fail`, `@venusprotocol/venus-periphery@1.4.0-dev.1`'s
  `yarn patch-package`, `@sincpro/mobile-ui@3.0.1`'s `if command -v patch-package ...`): the
  owner keeps `node_modules` patchers reported (rejected explanation of patchers); v1's bare
  `patch-package` predates that ruling and is left as it is.
